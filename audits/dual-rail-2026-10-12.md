## Checked and clean

- **The replay guard after #12, which is the whole of "one payment, one
  call".** `_resource_of` (`adapter.py:216`) now keys on
  `SCRIPT_NAME + PATH_INFO` and nothing a payer sends — the `Host:` and
  `X-Forwarded-Proto` headers that bought a call per spelling are gone. Every
  step of `resource_key` (`verify.py:57`) merges keys and none splits one, so
  it can only refuse more. I re-derived the Python/Node equivalence by hand
  rather than taking the conformance test's word for it: the two apply the
  decode and the canonicalisation in a different ORDER (Node percent-decodes
  the raw target then canonicalises; Python receives PATH_INFO already decoded
  per PEP 3333 and canonicalises that), and I could not find an input where
  that order changes the key — `%3F`, `%23`, `%2F%2F`, a literal query, an
  absolute-form request line and a latin-1 high byte all land in the same
  bucket on both sides, and both lowercase ASCII only.
- **`verify.verify` cannot be made to accept the wrong thing.** Confirmed is
  read off the node and never defaulted; a non-send is refused by name rather
  than falling through to "underpaid"; `payTo` is checksum-checked before the
  comparison so a seller's own misconfiguration is not reported as the payer's
  fault; `_same_account` compares decoded public keys, so `xrb_`/`nano_`
  spellings match and a non-address matches nothing; the amount comparison is
  `int` raw with `>=`, and underpayment by one raw is underpayment.
- **The fall-open contract holds, including against a lying node.** I went
  looking for a way to turn a Nano-side failure into a 5xx on the seller's
  USDC path, because that is the objection the adapter's own first paragraph
  answers. `read_block_info` (`nanonode.py:49`) calls `.get` on the decoded
  reply, so a node or gateway answering HTTP 200 with valid JSON that is *not*
  an object raises `AttributeError` rather than `NodeError` — but
  `check_payment` (`adapter.py:107`) catches bare `Exception` and falls
  through, and `_patched` likewise returns the body untouched on anything it
  does not understand. So the hole exists one layer down and is closed one
  layer up. Worth knowing it rests on that broad catch and not on
  `nanonode.py`. (The same shape in `nano-finality-proof` has no such catch
  above it, and is fixed there today in
  `dhyabi2/nano-finality-proof#6`.)
- **The appended entry's `resource: null`, measured against the real x402
  package rather than argued.** `resource_of` reads the resource string out of
  the seller's existing entries, so on an x402 **v2** challenge — where
  `resource` is a top-level object, not a per-entry field — the appended entry
  carries `"resource": null`:

  ```
  $ python3 -I probe_resource.py
  v2 challenge, top-level resource: {"url": "https://seller.example/api/report"}
  appended entry's resource field : null
  is the key present?             : True
  ```

  I expected this to be a defect and it is not. Installed `@x402/core@2.28.0`
  and put the emitted entry to its own schemas:

  ```
  resource: <url>  (v1 seller, copied)         V1=ok    V2=ok    union=ok
  resource: null   (v2 seller, emitted today)  V1=FAIL  V2=ok    union=ok
  resource absent  (v2 seller, proposed)       V1=FAIL  V2=ok    union=ok
  ```

  V1 requires `resource` as a string, so it rejects the null **and** the
  absent key alike; V2 accepts both. Omitting the key would therefore buy
  nothing a client can observe, and a v1 seller's entries always carry a
  resource to copy. **No change is warranted**, and this is written down so
  the next run does not spend the same hour on it.
- **`network.classify` fails closed.** A bare `nano`/`xno` is
  `network_unspecified` and `nano:testnet` is `not_mainnet`, both distinct
  from `not_nano`, and neither is folded to mainnet — correct, since Nano's
  test networks share the `nano_` address prefix. `find_nano` matches both live
  spellings, so a seller already accepting XNO as `nano-mainnet` does not get a
  second Nano entry appended beside theirs. An underscore spelling
  (`nano_mainnet`) would be missed and would get a second entry — I am
  deliberately **not** adding it: the module's rule is that a spelling is
  added only on evidence from a shipped package or a real payer, and I have
  none for that one. Inventing spellings widens what is folded to mainnet on a
  guess about where money goes.
- **`append_nano` is incapable of altering an existing rail.** It deep-copies,
  appends last, returns the input unchanged when a Nano entry is already
  present, and `assert_additive` raises unless the prefix is deeply equal and
  exactly one element was added.
- **Amounts.** `money.py` is integer raw throughout; `xno_to_raw` refuses a
  float by type before any arithmetic and parses the decimal string with an
  ASCII-only grammar (so a Unicode digit is refused rather than silently
  accepted by `isdigit()`); `raw_to_xno` refuses a non-int. The entry
  advertises raw under both `amount` and `maxAmountRequired`, with the decimal
  figure only in `maxAmountRequiredFormatted`.
- **`verifiers.py` reports an unreachable check as unreachable, never as a
  pass**, and both the node read and the README fetch are injected.
- **README URLs** all resolve; the two GitHub 403s are this session's proxy,
  not 404s.
