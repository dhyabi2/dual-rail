# dual-rail — audit 2026-10-09

Previous audit 2026-10-07. Read through one question: can an agent pay in XNO with this, today,
without being hurt?

HEAD audited: `5387e62` ("check: read a resources[] catalogue instead of calling it empty (#7)").
Python 3.11 / Node 22, standard library only in both.

**Nothing worth changing.** This file is the whole result; no production line is touched. The one
defect the 2026-10-07 audit left open has since been fixed, and that was confirmed here rather
than taken on the commit subject's word.

## Checked

- **The documented quickstart, run exactly as the README prints it**, and its three counts
  against what the README claims:

  | README says | measured |
  | --- | --- |
  | `python3 -m unittest discover -s tests` — 137 tests | **Ran 137 tests — OK** |
  | `(cd node && npm test)` — 75 tests | **# tests 75 / # pass 75 / # fail 0** |
  | `python3 tests/capture_live_verify.py` — 7/7 verify | **exit 0**, adapter mounted on a real loopback socket |

  All three match. The README states its own test counts, so it goes stale silently if a suite
  grows; it has not.

- **The 2026-10-07 audit's one remaining open item is fixed.** It recorded that `cli.py check` was
  blind to the `resources[]` catalogue shape where `inspect` and `add` were not, and so answered
  `accepts[] entries: 0 / entries naming Nano: 0 / check: NOT payable as it stands` on a manifest
  that was in fact payable — a false negative on plausibly the first command an operator runs. It
  was left for "a run that takes it as its own piece of work", because `declaration.py` is
  cross-checked against `@x402/core` over 120,000 near-valid documents and widening the validator
  is careful work.

  PR #7 did it. Re-run here against a two-resource catalogue whose second resource carries a
  `nano:mainnet` entry:

  ```
  document:              resource catalogue, 2 resource(s)
  accepts[] entries:     2 across all resources
  resources naming Nano: 1, of which not payable: 0
  check: payable - an x402 client would pay the Nano entry of every resource in this catalogue
  ```

  It reports per-resource rather than flattening, which is what `inspect` already did. Nothing to
  carry forward; the note is closed.

- **`money.py`, probed rather than read.** Integers only; a `float` is refused by name
  (`float_amount`) before anything else; a decimal string is parsed by hand with an ASCII-only
  grammar, so no `Decimal` context precision can apply — it does not have the process-global
  `prec` defect that `nano-mcp-public`, `langchain-vend`, `gpt-researcher-x402-retriever` and
  `openai-agents-nano-x402` each carried. Measured on this tree:

  - accepted exactly: `1` → `10**30`, `0.0001` → `10**26`, `.5` → `5·10**29`,
    `0.000000000000000000000000000001` → `1` raw, `1.` → `10**30`;
  - refused with a reason: `1.0` and `0.0001` as floats (`float_amount`), 31 decimal places,
    `1e5`, `+1`, `-1`, `1_000`, `0x10`, `.`, empty, and the Unicode digits `٣` and `²`
    (the latter being the one that used to crash out of the module past every `except
    AmountError`, per the comment in place);
  - `raw_to_xno` / `xno_to_raw` round-trip exact at `10**30 + 1`, the value a 28-digit
    `Decimal` context loses.

- **`verify.py` trusts the ledger, not the payer.** Five questions, all from `block_info`: the
  block exists; the node calls it **confirmed**; it is a **send**; its destination decodes to the
  same public key as `payTo`; its amount is `>=` required, compared as integer raw. The payee is
  read off the send's `link_as_account`/`destination`, never off `block_account`, which on a send
  is the payer.

- **Both hard constraints.** Additive-only: `append_nano` deep-copies, never touches an existing
  element, appends last, and every emitting path runs `assert_additive`. Fails-open: every
  `NodeError` becomes `Unpaid` and `DualRail.check_payment` additionally catches `Exception`, so
  no Nano fault can become a 5xx for a customer paying in USDC — asserted by
  `test_node_outage_falls_through`, not just by the README paragraph that claims it.

- **Secrets.** None in the tree. The adapter holds no key and never sends.

## Could not verify

- **No live x402 endpoint was paid and no XNO moved.** `capture_live_verify.py` runs against
  `fakenode` on a loopback socket, so no facilitator and no ledger were involved. This
  environment's network policy reaches neither. Unchanged standing caveat.
- **The `@x402/core` and `@x402nano/exact` schemas were not re-read first-hand** (no npm registry
  read attempted this run). `challenge.py` cites `@x402/core` 2.28.0 and `@x402nano/exact` 0.3.0,
  and `tests/test_dual_rail.py` pins both required field sets locally; that local pin is what was
  exercised here.
- **`read_block_info` outside `HttpNanoNode.block_info`'s `try`**, noted by the 2026-10-07 audit
  as costing a worse log reason but no behaviour an agent can feel. Re-read and still agreed with:
  `check_payment`'s `except Exception` holds constraint 2 on every mounted path. Not changed, for
  the same reason as last time — it is a readability change on the money path.
- **`MIN_PRICE_XNO` / `MAX_PRICE_XNO`** (0.000001 to 100 XNO) are a config-time band, unchanged,
  and whether that band suits a pay-per-call price is a product question, not assessed.
