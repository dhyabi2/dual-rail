# dual-rail - audit 2026-10-07

Previous audit 2026-10-03. Read through one question: can an agent pay in XNO with this, today,
without being hurt?

HEAD audited: `0149e4b` ("A receive block is not a payment: read the payee off the send, not off
the account (#5)"). Python 3.11 / Node 22, standard library only in both.

**Found nothing worth changing on the paying path.** This file is the whole result; no production
line is touched. One known defect is confirmed still live and is left where the last run left it -
see issue #1 below.

## Checked

- **The documented quickstart, run exactly as the README prints it.**
  `python3 -m unittest discover -s tests` **109 passed**, `(cd node && npm test)` **67 passed,
  0 failed**, `python3 tests/capture_live_verify.py` **7/7, exit 0**. All three match the counts
  the README claims, which were 34 / 22 / 7 at the last audit - the repository has roughly tripled
  its suite since and kept the README honest.
- **Issue #1: three of its four items hold on `main`; one is still open, and the issue stays
  open.** The 2026-10-04 comment on it says so and names the remaining item; this run measured
  all four rather than taking that comment's word for it.
  - *emit `amount` in raw for a v2 manifest* - `nano_entry` emits **both** names, `amount` and
    `maxAmountRequired`, each the integer raw string, with the decimal kept beside it in
    `maxAmountRequiredFormatted`. Carrying both is right rather than lazy: we append to somebody
    else's challenge whose protocol version we do not choose, each version's schema strips the
    other's field rather than rejecting it, and carrying only one is rejected outright by the
    other version. `maxTimeoutSeconds` is there too, which v1 and v2 both require.
    Verified by running `cli.py add --diff` against a v2 manifest: `"amount":
    "100000000000000000000000000"` for 0.0001 XNO, and the existing `eip155:8453` entry comes back
    byte-identical.
  - *make `inspect` read both fields* - `AMOUNT_FIELDS = ("amount", "maxAmountRequired",
    "max_amount_required")`, in feeless402's own order, and `inspect` reports `amount_field` so a
    reader can see which name answered. The v2 entry that used to report `maxAmountRequired: null`
    now reports `"amount": "10000", "amount_field": "amount"`.
  - *`inspect` answered `no accepts[] array` for a multi-resource manifest* - `_resource_sections`
    handles `resources[]`, and `inspect` reports `multi_resource: true` with one section per
    resource rather than flattening them, which would invent an `accepts[]` no client ever sees.
    Verified against a two-resource manifest.
  - *a conformance test against a real nano:mainnet 402* - the repository has the Python/Node
    conformance run and `capture_live_verify.py` against a loopback server. A live paid 402 is
    still not reachable from a cloud session (see "Could not verify"), so that part stands as the
    standing caveat rather than as an open defect.

  **Still open, and measured this run:** `cli.py check` is blind to the multi-resource shape, where
  `inspect` and `add` are not. On a two-resource manifest it answers

  ```
  accepts[] entries:     0
  entries naming Nano:   0
  [document] accepts     accepts must be an array of entries; got null
  check: NOT payable as it stands
  ```

  which tells an operator their 402 cannot take a Nano payment when nothing of the sort has been
  established - and `check` is plausibly the first command they run. That path is in
  `declaration.py`, which is cross-checked against `@x402/core` 2.28.0 over 120,000 near-valid
  documents, so widening what it accepts is a careful change and not one to make at the end of an
  audit run: done badly it would weaken the validator that everything else leans on. **Left for a
  run that takes it as its own piece of work**, which is where the 2026-10-04 comment left it too.
  This audit's contribution is to confirm the symptom still reproduces on `0149e4b` rather than
  letting the note go stale.
- **Amount handling.** `money.py` is integers only, refuses a `float` outright with a named
  reason, parses a decimal string by hand (no float, no `Decimal` context to get wrong - so it
  does not have the process-global `prec` defect that `nano-mcp-public`, `langchain-vend` and
  `gpt-researcher-x402-retriever` each had), and refuses a negative, a second `.`, a non-ASCII
  digit and more than 30 decimal places. The Node binding mirrors it in `BigInt` and the
  conformance suite asserts the two agree on values chosen to break a float.
- **Verification trusts the ledger, never the payer** (`verify.py`). Five questions, all from
  `block_info`: the block exists, the node calls it **confirmed**, it is a **send**, its
  destination decodes to the same public key as `payTo` (so `nano_`/`xrb_` spelling cannot refuse
  a payment that did arrive, and nothing wider), and its amount is `>=` required in integer raw.
  The `not_a_send` refusal is the one that matters and it is the subject of the last commit: a
  **receive on our own payout account** is confirmed, carries a real amount, and its hash is
  public in our account history - so before that check any stranger could read our ledger and be
  served for free. `read_block_info` reads the payee off the send's `link_as_account`/
  `destination` and never off `block_account`, which on a send is the payer.
- **Hard constraint 1 (additive only).** `append_nano` deep-copies, never touches an existing
  element, appends last, and every emitting path runs `assert_additive`, which re-checks the
  prefix element by element and the count. `find_nano` matches every spelling of Nano mainnet, not
  just the one we emit, so a seller who already accepts XNO as `nano-mainnet` does not get a
  second Nano entry appended beside theirs.
- **Hard constraint 2 (fails open).** `verify.verify` turns every `NodeError` into `Unpaid`;
  `DualRail.check_payment` additionally catches `Exception` and falls through, so a node that
  answers something unusable cannot become a 5xx for a customer paying in USDC.
  `_patched` leaves a 402 it does not understand exactly as it was.
- **Address handling.** `payTo` is checksum-validated at construction, so a service cannot boot
  advertising an address that can never receive. `on_verify_error` is pinned to one permitted
  value.
- **Secrets.** None in the tree. The adapter holds no key and never sends. `nanonode.host_of`
  strips credentials from a node URL before it reaches a log.

## One thing read and deliberately not changed

`read_block_info` is called **outside** `HttpNanoNode.block_info`'s `try`, so a node answering
`{"amount": "abc"}` or a non-mapping `contents` raises `ValueError`/`AttributeError` rather than
the `NodeError("node_unreachable", "...answered something unusable")` that exists for exactly
that case. It is not a live defect: `DualRail.check_payment`'s `except Exception` catches it and
falls through, so constraint 2 holds on every mounted path, and the suite's outage test passes.
What it costs is a worse reason in the log, and a `verify.verify` docstring ("Anything else ... is
not paid") that is true of the adapter but not of that function called directly. Tightening it
would be a readability change on the money path with no behaviour an agent can feel, so it is
written down here rather than turned into a pull request.

## Could not verify

- **No live x402 endpoint was paid and no XNO moved.** `capture_live_verify.py` mounts the adapter
  on a real loopback socket and verifies 7/7, but against `fakenode`, so no facilitator and no
  ledger were involved. This environment's network policy reaches neither.
- **The `@x402nano/exact` and `@x402/core` schemas were not re-read first-hand this run** (no npm
  from here). `challenge.py`'s docstring cites `@x402/core` 2.28.0's `PaymentRequirementsV1Schema`
  / `V2Schema` and `@x402nano/exact` 0.3.0's `parsePrice`, measured when the both-names change
  landed; that is a second-hand citation here, and `tests/test_dual_rail.py` pins both required
  field sets locally.
- **`MIN_PRICE_XNO` / `MAX_PRICE_XNO`** (0.000001 to 100 XNO) are a config-time band, unchanged,
  and whether that band is right for a pay-per-call price is a product question that was not
  assessed.
