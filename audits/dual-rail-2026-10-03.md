# dual-rail - audit 2026-10-03

First audit of this repository (published 2026-10-02; `audits/` did not exist). Read through one
question: can an agent pay in XNO with this, today, without being hurt?

HEAD audited: `a42765a`. Python 3.11 / Node 22, standard library only in both.

## Checked

- **The documented quickstart, run exactly as the README prints it.**
  `python3 -m unittest discover -s tests` **34 passed**, `node --test test/dual-rail.test.js`
  **22 passed**, `python3 tests/capture_live_verify.py` **7/7, exit 0** - all three match the
  counts the README claims. After this branch: **39** and **26**.
- **Amount handling.** `money.py` is integers only and refuses a `float` outright with a named
  reason; `xno_to_raw` parses a decimal string by hand (no `float`, no `Decimal` context to get
  wrong), rejects a negative, a second `.`, a non-digit and more than 30 decimal places. The Node
  binding mirrors it in `BigInt` and the conformance suite asserts the two agree on values chosen
  to break a float. Clean.
- **Hard constraint 1 (additive only).** `append_nano` deep-copies, never touches an existing
  element, appends last, and every emitting path runs `assert_additive`, which re-checks the
  prefix element by element and the count. Verified by hand that an existing USDC entry comes
  back byte-identical.
- **Hard constraint 2 (fails open).** `verify.verify` converts every node failure into `Unpaid`
  and never lets `NodeError` escape; `on_verify_error` is pinned to one permitted value at
  construction. `test_node_outage_falls_through` runs the whole flow with every node call raising.
- **Verification trusts the ledger, not the payer.** The destination, amount and confirmation all
  come from `block_info`; an unconfirmed block is refused; `ReplayGuard` scopes one payment to one
  resource, and its in-process limitation is stated in its own docstring rather than left to be
  discovered.
- **Address handling.** `payTo` is checksum-validated at construction, so a service cannot boot
  advertising an address that can never receive.
- **Secrets.** None in the tree. The adapter holds no key and never sends.

## Found and fixed (open for review - it changes an advertised amount)

**The entry this adapter appends could not be paid by any x402 Nano client**
(`challenge.py:38`, `node/challenge.js:30`, fixed on `fix/advertise-the-amount-in-raw`).

`nano_entry` wrote the operator's configured decimal XNO string into
`maxAmountRequired` verbatim:

```python
"maxAmountRequired": str(amount_xno),      # "0.0001"
...
"extra": {"decimals": 30, ...}
```

`maxAmountRequired` is the amount in the asset's **atomic** unit - that is what `decimals` is
there to declare, and it is the convention the USDC entries beside it already use (`"10000"` is
0.01 USDC at 6 decimals). For XNO the atomic unit is raw, 10**30 to the XNO. Every x402 Nano
client reads the field as an integer count of raw; the reference client, feeless402 0.2.12 - the
one `openai-agents-nano-x402`, `langchain-vend` and `gpt-researcher-x402-retriever` all pay
through - reads it literally:

```python
def offer_amount_raw(offer: dict) -> int:
    for field in ("amount", "maxAmountRequired", "max_amount_required"):
        if field in offer:
            return int(offer[field])
```

Measured, against the installed package, on the exact entry this adapter emits:

```
feeless402 picks the Nano offer OK: nano:mainnet XNO
payTo reads fine: nano_3t6k35gi95xu6te...
now the amount:
  ValueError: invalid literal for int() with base 10: '0.0001'
```

So an agent that found the XNO rail, accepted it and read the payee correctly **crashed on the
price** - an uncaught `ValueError` inside the payer, not a clean refusal. That is the one thing
this adapter exists to make possible.

**The seller was never at risk,** which is why no test caught it: the adapter checks a payment
against `money.check_price(amount_xno)` on its own config, not against the advertised string, so a
payer that had read "0.0001" as raw and sent 10**-4 raw would have been refused as underpaid. The
loss was the sale, not the money - and it was silent on the merchant's side.

Fixed by emitting the atomic figure, with the decimal kept beside it in
`maxAmountRequiredFormatted`, which is where feeless402's `compare_rails` already looks for
something human-readable:

```
"maxAmountRequired": "100000000000000000000000000",
"maxAmountRequiredFormatted": "0.0001 XNO",
```

After it, the same reference client reads `100000000000000000000000000` raw = exactly 0.0001 XNO,
`compare_rails` renders `0.0001 XNO`, and the USDC entry is still byte-identical. The configured
`amountXno` is unchanged, and so is every amount this adapter accepts.

Nine tests added (five Python, four Node), each failing with its own binding's production change
reverted alone. The repository's own conformance test also fails on a one-sided change, so the
two bindings cannot drift apart on this.

**Not merged by this run.** It changes the amount a payer is told to send, which is outside what a
routine may merge on its own, however plainly a unit correction it is. One sentence of review is
all it needs: is raw the right wire unit for `maxAmountRequired`? Everything above says yes.

## Could not verify

- **No live x402 endpoint was paid.** The break and the fix are both measured against the
  installed `feeless402` 0.2.12 reading the adapter's real output, not against a server settling
  a block. `tests/capture_live_verify.py` mounts the adapter on 127.0.0.1 and verifies 7/7, but
  with `fakenode`, so no XNO moved and no facilitator was involved.
- **The `@x402nano/exact` JS schema was not read first-hand** in this run (no network access to
  npm from here). `openai-agents-nano-x402#17` reports it measured `NANO_SEND_BLOCK` against
  `@x402nano/exact` 0.3.0 and states the same rule - the amount is an integer string in raw -
  which agrees with feeless402, but that is a second-hand citation here.
- **`MIN_PRICE_XNO` / `MAX_PRICE_XNO`** (0.000001 to 100 XNO) are a config-time band and are
  unaffected; whether that band is right for a pay-per-call price was not assessed.
