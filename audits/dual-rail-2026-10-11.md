## Found and fixed — one payment bought as many calls as the payer cared to ask for

The replay guard is the whole of "one payment, one call". `ReplayGuard` buckets spent block hashes
by a **resource string the adapter derives from the request**, and both bindings derived it from
headers the payer sends:

```python
# adapter.py:195 on master
def _resource_of(environ) -> str:
    scheme = environ.get("wsgi.url_scheme", "http")
    host = environ.get("HTTP_HOST") or environ.get("SERVER_NAME", "")
    return "%s://%s%s" % (scheme, host, environ.get("PATH_INFO", ""))
```

```js
// node/dual-rail.js:247 on master
function resourceOfRequest(req) {
  const host = req.headers.host || '';
  const proto = req.headers['x-forwarded-proto'] || (req.socket && req.socket.encrypted ? 'https' : 'http');
  return `${proto}://${host}${(req.originalUrl || req.url || '').split('?')[0]}`;
}
```

`HTTP_HOST` is the payer's own `Host:` header. `wsgi.url_scheme` behind a proxy is set from
`X-Forwarded-Proto`, and the Node binding reads that header by name. So a payer who had paid **once**
could present the same confirmed send again under any `Host:` it liked, land in a different bucket of
the guard, and be served again for nothing.

Measured on `master`, one real confirmed send of 0.0001 XNO to the seller's `payTo`, the exact price,
nine requests to the same path, nothing varying but the `Host:` header:

```
ONE payment of 0.0001 XNO was made. Block 9F2C00000000...

  Host: example.dev        -> 200 SERVED
  Host: example.dev.       -> 200 SERVED
  Host: EXAMPLE.DEV        -> 200 SERVED
  Host: example.dev:80     -> 200 SERVED
  Host: anything-at-all    -> 200 SERVED
  Host: example.dev:443    -> 200 SERVED
  Host: x                  -> 200 SERVED
  Host: y                  -> 200 SERVED
  Host: z                  -> 200 SERVED

paid for : 1 call
served   : 9 calls
```

Nine is not the limit; the limit is how many distinct strings the payer can be bothered to send. The
block is a genuine, confirmed, correctly-addressed, exactly-priced send every time — every one of
`verify.py`'s four yes-questions answers yes, and the one that must answer no (`replayed`) never gets
the chance, because the guard is looking in the wrong bucket. This is a payment accepted where it
should be refused, and the quantity accepted is unbounded.

**Fixed** by keying the guard on the request path alone, in both bindings:

```python
return environ.get("PATH_INFO", "") or "/"
```

```js
return (req.originalUrl || req.url || '').split('?')[0] || '/';
```

A `DualRail` carries one `payTo` and one price, so one instance is one seller's. The host says
nothing about *which* of that seller's resources was bought; only the path does. **The new key is
strictly coarser than the old one** — the old key contained the path, so any two requests that shared
the old key share the new one — therefore the change can only ever refuse more and admit less. It
cannot widen what is accepted, and it moves no amount, destination, rounding or key path.

Six tests added, four Python and two Node. **Three Python and one Node fail with the production file
alone reverted to `master`** and pass with it restored:


## Checked and clean

- **The key is only ever the guard's key.** `grep -rn "_resource_of"` outside `tests/` is its
  definition and the one call at `adapter.py:135`; `resourceOfRequest` likewise at
  `node/dual-rail.js:273`. It never reaches a client, a log line or the 402 body. The `resource`
  field of the appended `accepts[]` entry comes from `challenge.resource_of(accepts)`, which reads
  the manifest's own existing entries, so the advertised challenge is untouched by this change —
  `test 2` of the Node suite (`accepts.at(-1).resource === 'https://example.dev/report'`) still
  passes unchanged.
- **Amounts are integers end to end.** `money.py` refuses a `float` outright (`xno_to_raw`,
  `raw_to_xno`), parses a decimal **string** with an ASCII-only grammar, and is integer arithmetic
  throughout (`int(whole) * 10**30 + int(frac.ljust(30, "0"))`). No `decimal` import anywhere, so
  the 28-digit process-global-context rounding found in the sibling repositories cannot be present.
  The Node binding uses `BigInt` and the conformance suite asserts the two agree on values chosen
  to break a double.
- **`confirmed` is normalised, not read for truthiness.** `nanonode.read_block_info:62` is
  `str(answer.get("confirmed", "false")).lower() == "true"`, so a node answering the string
  `"false"` — which is truthy in Python — is correctly read as unconfirmed, and a missing field
  defaults to unconfirmed. The kind of a block is read off the block (`subtype` or, for a legacy
  block, `contents.type`) and never defaulted.
- **Verification trusts nothing the payer submitted** beyond the block hash, which is then looked up
  at the node. The destination is compared by decoded public key (`verify._same_account`), so an
  `xrb_`/`nano_` spelling cannot make the payee diverge; a destination that is not an address
  decodes to nothing and equals nothing. A non-`send` is refused by name rather than falling through
  to "underpaid". The payee is never read from `block_account`.
- **Our rail cannot cost them a USDC sale.** `DualRail.check_payment` catches `Unpaid` *and* bare
  `Exception` (`adapter.py:104-109`) and returns `None` either way, so nothing from the Nano side can
  become a 5xx. This also contains the one rough edge found while reading `nanonode`: `read_block_info`
  computes `int(answer["amount"])` outside the `try` that wraps the HTTP call, so a node answering a
  non-integer `amount` raises a bare `ValueError` out of `block_info` rather than a `NodeError` —
  which the bare except turns into a fall-through, the correct outcome. Not a defect in what ships;
  recorded because the contract in `nanonode`'s docstring ("every failure is a `NodeError`") is
  narrower than the code.
- **No shell and no path sink.** `grep -rn "os.system\|subprocess\|shell=True\|eval(\|exec(\|pickle\|
  __import__"` over the production files finds only `cli.py`'s `subprocess` for its own
  self-test invocation; nothing a payer submits reaches a shell, a path or an interpreter.
- **No committed secret.** Nothing matching `*.key`, `*.pem`, `.env`, `seed`, `secret` or
  `credential` with a value, in the tree or across the cloned history. `nanonode.host_of` exists
  precisely to strip `user:key@` credentials out of a node URL before it is logged, and is tested.
- **The README's own counts are honest.** It prints `# 150 tests` and `# 75 tests`, and that is
  exactly what the two suites ran before this change (the 2026-10-09 audit's "137" is stale against
  a README that has since been corrected, not against the code). This PR takes them to 154 and 77
  and updates both lines.

## Could not verify

- **No live Nano node.** `rpc.nano.to` and the other public nodes are outside this environment's
  network policy, so every finding above is proved against `fakenode.FakeNode` and the recorded
  reply shapes in `read_block_info` — which is where this defect lived, since the guard never asks
  the node anything. The defect does not depend on a node's behaviour at all.
- **Only Python 3.11.17 and Node 22 were run.** CI's other legs (3.8/3.10/3.12/3.13, Node 18/20) are
  unproven from here. The change is one `dict.get` and one `String.split` and uses no syntax newer
  than either floor.
- **Whether a deployment exists that relies on the old per-host bucketing.** One `DualRail` instance
  is one `payTo` at one price, so a genuine multi-tenant arrangement needs one instance per tenant
  and keeps its own guard either way. No shipped example mounts one instance across hostnames.
